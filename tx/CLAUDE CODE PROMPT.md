## What you're building

A monolithic, fully async **FastAPI** application (Python 3.12) for "EduGroup" — an online tutoring platform with 4 roles (student, teacher, manager, superadmin), built around courses → groups → lessons, enrollment + simplified manual payments (with optional installments and a group waitlist), background jobs for waitlist/expiry housekeeping, and a **server-rendered Jinja2 frontend that lives inside the same FastAPI app** — no separate SPA, no client-side REST/AJAX layer. Every page is a FastAPI route that calls the service layer directly and renders HTML; every mutating action is a plain HTML `<form method="post">`.

## Hard requirements (non-negotiable)

1. **Async FastAPI + SQLAlchemy 2.0 (async, asyncpg) + Alembic** migrations, PostgreSQL 16.
2. **JWT via `python-jose`** (`HS256`), access token (30 min) + refresh token (7 days), both delivered as `httpOnly`, `Secure`, `SameSite=Lax` cookies. Passwords hashed with `passlib[bcrypt]`.
3. **Refresh token rotation + blacklist/revocation**: a `RefreshToken` table (hashed tokens only), rotation on every `/auth/refresh`, `/auth/logout` revocation, and reuse-detection that revokes all of a user's tokens if a already-revoked token is replayed.
4. **Rate limiting** on `/auth/login` and `/auth/register/*` via `slowapi` (429 on limit breach), **backed by Redis storage** (`storage_uri="redis://redis:6379/0"`), not in-memory — see TZ 7 / 8.2.
5. **Frontend is 100% server-side rendered Jinja2** under `templates/` + `static/`, following the exact folder structure and page map in TZ section 14. The browser never calls a JSON endpoint via `fetch`/AJAX for data or auth — every page is rendered server-side by a FastAPI route that calls the relevant module's `service.py` functions directly (not via HTTP). All mutating actions are POST forms using the Post/Redirect/Get pattern. Vanilla JS is used only for pure UI interactivity (modals, tabs, client-side validation hints, confirm dialogs) — never for fetching data or attaching auth headers. **Every page/form listed in TZ section 14.3 must exist, including the ones marked "(YANGI, v2.0)"** — profile edit, course/group/lesson edit forms, group status (close/archive) controls, teacher waitlist view, manager/superadmin enrollment list, `/reports/groups/{id}` and `/reports/teachers/{id}` pages, "mark all notifications read", superadmin manager-management UI, and the enrollment-cancel form. No JSON API endpoint from section 6 (including the new 6.11 superadmin endpoints) should be left without a corresponding frontend page/form — cross-check TZ 14.3's table against TZ section 6 endpoint-by-endpoint before considering the frontend done.
6. **The JSON API described in TZ section 6 must still exist and work** (it's reused internally by the web layer's service calls, and is there for tests/future clients) — but it is architecturally separate from the web page routes (`app/web/`), which are POST-only for mutations per the reasoning in TZ 14.1.
7. **Soft delete + audit log**: `Course`, `Group`, `Lesson` use `deleted_at` instead of hard deletes; every create/update/delete/restore on them writes an `AuditLog` row.
8. **Waitlist**: enrollment requests on a full group (`awaiting_payment` + `active` count ≥ `capacity` — TZ 9) get `status=waitlisted` with a `waitlist_position` instead of a `400`; when a slot frees up (cancellation, forced cancel, or automatic expiry), the earliest waitlisted student is auto-promoted (TZ 3.11).
9. **Partial payments / installments**: a student can pay in full or set up a 2–4 part `PaymentPlan`/`Installment` schedule (only while `enrollment.status == awaiting_payment` — TZ 9); the enrollment activates on the first confirmed payment; `PaymentPlan.status` auto-completes when the last installment is paid; a rejected payment does **not** change the enrollment's status; overdue installments are flagged and notified via a Celery beat task, not per-request.
10. **In-app notifications**: a `Notification` model/module triggered synchronously by other services on every meaningful state change (approvals, payment confirm/reject, waitlist promotion, group assignment, new lesson, overdue installment, enrollment expiry, account block/unblock). Notification creation stays **synchronous** — do not route it through Celery (see TZ 8.2 for the reasoning; don't second-guess this).
11. **`LessonProgress` is required, not optional** — students' watched status is tracked and teachers can see per-student progress per group.
12. **`Enrollment` uniqueness uses a partial unique index** (`WHERE status IN ('awaiting_payment','waitlisted','active')`), **not** a plain table-level unique constraint on `(student_id, group_id)` — TZ 4.7/9. Getting this wrong silently breaks re-enrollment after a cancellation, so implement it as a real Postgres partial index via Alembic, and add the `test_reenroll_after_cancel.py` test to prove it works.
13. **Celery + Redis for background jobs** (TZ 8.2): a `celery_worker` and `celery_beat` service, broker/result backend = Redis. Two periodic tasks only: `enrollments.tasks.expire_stale_enrollments` (hourly — expires stale `awaiting_payment`/`waitlisted` enrollments past `ENROLLMENT_REQUEST_EXPIRY_HOURS` and promotes the next waitlisted student) and `payments.tasks.flag_overdue_installments` (daily — flags overdue installments and notifies). Celery workers are **synchronous** processes — do not try to reuse the app's async `asyncpg` session inside a task; build a separate sync SQLAlchemy engine/session (`app/db/sync_session.py`, `psycopg`/`psycopg2` driver) for task use, reusing the same model classes. Do not put anything else on Celery (see item 10 above) — this keeps the architecture easy to explain and defend (see `code_explanation.md` requirement below).
14. **Superadmin user/manager management** (TZ 6.11, new in v2.0): `POST /superadmin/managers` + `GET /superadmin/managers` to create/list manager accounts (superadmin is the only way managers get created — there is no self-registration for that role), and `POST /superadmin/users/{id}/block` / `.../unblock` to block/unblock any account. A blocked user must get `403` on login and on `/auth/refresh`.
15. Every business rule, model, endpoint, and validation rule in `TZ.md` sections 2–16 must be implemented — do not skip anything on the theory that it's "optional" unless the TZ itself explicitly marks it out of scope (section 15).
16. **Deliver a `code_explanation.md` file at the repo root** — see the dedicated section below. This is not optional documentation fluff; treat it as a first-class deliverable with the same seriousness as the code itself.

## `code_explanation.md` — required deliverable (exam-prep documentation)

This file is being built for a final exam where the author (a solo developer) will be asked to explain any part of this codebase out loud, under questioning. Its job is different from `README.md`: the README says *where things are*; `code_explanation.md` says *why the code is written the way it is, and how it actually works*, in enough depth that someone could defend every design choice on the spot. Write it as if you're personally tutoring the person who will be examined on this exact code.

Structure it as follows:

1. **Architecture overview** — why layered `models → schemas → repository → service → router`, why async SQLAlchemy, why Jinja2 SSR instead of a SPA, why JSON API and web routes are kept separate but share `service.py`. Explain the trade-offs, not just the choice.
2. **Per-module walkthrough** (one subsection per `app/<module>/`, in dependency order — same order as TZ section 3): what each model field is for, the non-obvious business rules the service layer enforces (waitlist promotion, the partial unique index and why a plain unique constraint would be a bug, the `awaiting_payment`+`active` capacity rule, PaymentPlan auto-completion, why a rejected payment doesn't change enrollment status), and what each router endpoint does and why it has the permission checks it has.
3. **Auth deep dive**: the full JWT lifecycle — access + refresh token issuance, `httpOnly`/`Secure`/`SameSite=Lax` cookies, refresh rotation, reuse-detection and full-revocation, rate limiting via Redis. Walk through what happens on each of: normal login, normal refresh, refresh-token replay (reuse), logout.
4. **Celery/Redis deep dive**: why these two specific periodic tasks and no others, why notifications and audit logs stay synchronous, why Celery needs its own sync DB session alongside the app's async one, and what would break if that separation weren't there.
5. **Frontend/SSR deep dive**: how a page route calls `service.py` directly instead of doing `fetch()`, why mutations are POST-only forms with Post/Redirect/Get, how cookie-based auth differs from a header-based JSON API client.
6. **Testing strategy**: what each major test file actually proves, and why the happy-path/failure-path pairing matters.
7. **Likely exam questions** (short section, optional but encouraged): a handful of the kind of "why did you do X instead of Y" questions an examiner might ask about the trickier decisions (partial unique index, sync vs async sessions in Celery, why installment overdue-checking is a periodic task rather than checked per-request), each with a 2–4 sentence model answer.

Keep the tone plain and direct — this is a study aid, not marketing copy. Reference actual file paths and function names throughout so it's easy to jump from the explanation to the code. Write it once the codebase is stable (last step in the process above), so it reflects what was actually built, not what was planned.

## Quality bar

Write this the way a senior FastAPI engineer would ship it for production, not a tutorial-grade demo:
- Full type hints, Pydantic v2 schemas for every request/response, no bare `dict` payloads.
- Dependency-injected DB sessions and current-user/role checks — no manual session handling scattered in routers.
- No business logic duplicated between the JSON API routers and the web page routers — both call the same `service.py` functions.
- Meaningful error handling (403/404/400/422/429) with clear messages, not generic 500s.
- Alembic migrations that actually match the models (don't hand-wave the schema), including the `Enrollment` partial unique index (raw SQL/`op.execute` in the migration, since Alembic's autogenerate doesn't reliably create partial indexes from ORM annotations alone).
- Docker Compose that runs cleanly with `docker compose up` on a clean checkout, including running migrations and bringing up `redis`, `celery_worker`, and `celery_beat` alongside `app`/`db`.
- Celery tasks are testable without a running broker — write them so the core logic is a plain function taking a `Session`, with a thin `@celery_app.task` wrapper around it, so tests can call the logic directly.
